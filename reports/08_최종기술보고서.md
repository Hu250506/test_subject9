# 콩잎 질병 분류 Vision AI API 서비스 기술보고서

## 1. 프로젝트 정보
- 프로젝트: ResNet18 기반 Beans 3클래스 분류 및 동기·비동기 서빙
- 입력: JPG/PNG/WEBP (5MB 이하)
- 출력: angular_leaf_spot / bean_rust / healthy
- 모델: microsoft/resnet-18 → artifacts/beans_resnet18
- 실행구조: FastAPI·Celery Worker(WSL2 `.venv`) + Redis·PostgreSQL(Docker)
- 실행환경: Windows + WSL2 Ubuntu 22.04.5 LTS, Python 3.10.12, Intel Core i7-12700, RAM 15GiB, CPU 추론

## 2. 모델 학습 결과 요약
| 항목 | 결과 |
|---|---|
| 학습 방식 | Backbone Freeze / Head-only (`--freeze-backbone`) |
| 실행 설정 | epochs 3, batch size 8, learning rate 2e-4 |
| Train 수 | 1,034 (폴더 파일 수 1,035, 확장자가 `.120tore`인 1개는 학습 필터에서 제외) |
| Validation 수 | 133 |
| Best Validation Accuracy | 0.7669 (Epoch 2, 3 동일) |
| Test 성능 | 미측정 |
| 모델 파일 | artifacts/beans_resnet18/model.safetensors |

- 근거 문서: [산출물 1](01_FineTuning_결과보고서.md)
- 원본 기록: artifacts/beans_resnet18/training_report.json
- Full Fine-tuning 비교 실험은 수행하지 않았다.

## 3. 아키텍처 및 데이터 흐름
- 동기: Browser → FastAPI → Redis 캐시 → (MISS) ResNet18 → JSON
- 비동기: Browser → FastAPI → 이미지 저장 + DB 작업(queued) → Redis 브로커 → Celery Worker → 캐시/모델 → DB(done) → `job_id` 상태 조회
- FastAPI와 Worker는 별도 프로세스이므로 모델이 각각 로드된다.
- 근거 문서: [산출물 2](02_시스템_아키텍처.md)

## 4. API·DB 설계
- 핵심 API: `GET /health`, `POST /api/sync/classify/`, `POST /api/async/classify/`(202), `GET /api/async/jobs/{job_id}/`
- 오류 처리: 잘못된 이미지 400, 5MB 초과 413, 없는 작업 404, 큐 등록 실패 503
- DB: PostgreSQL `image_jobs` (상태 `queued → running → done/failed`). 조회 시점 job 1~8이 모두 `done`, `failed` 행 없음
- 근거 문서: [산출물 3](03_API_명세서.md) / [산출물 4](04_DB_구조_작업이력.md)

## 5. 실제 버튼 처리 검증
- 동기식: 분류가 끝난 뒤 HTTP 200으로 결과를 응답
- 비동기식: HTTP 202와 `job_id`를 먼저 받고, 상태 조회로 `done`을 확인
- 근거 문서: [산출물 5](05_AI버튼_처리흐름.md)

## 6. 실제 성능 비교
| 항목 (중앙값, 조건별 5회, 워밍업 제외) | 값 |
|---|---:|
| Sync MISS HTTP 완료 | 24.16ms |
| Sync HIT HTTP 완료 | 2.08ms |
| Async MISS HTTP 접수 | 9.25ms |
| Async MISS 최종 확인 | 66.58ms |
| Async HIT 최종 확인 | 67.94ms |

- 비교 결론: 접수와 처리 분리 효과로 접수 응답이 61.71% 짧았으나 최종 확인은 더 길었다. 모델 추론 가속은 확인되지 않았다(추론시간 18.28ms 대 17.85ms).
- 근거 문서: [산출물 6](06_성능비교_보고서.md)

## 7. 기능 테스트·오류 조치
- 실환경 통합 테스트(헬스, 동기·비동기 분류, DB 기록, 불량 입력 400, 없는 작업 404, 캐시 MISS→HIT, Worker 중지 시 `queued` 유지 후 재실행 `done`)와 모의 테스트(4 passed)를 구분해 기록했다.
- 오류 조치: 동기 API가 캐시를 쓰지 않던 문제(`router_sync.py` 교체), `ImageJob` 누락, `base.html` 중복, Docker WSL 연동
- 근거 문서: [산출물 7](07_기능테스트_오류분석.md)

## 8. 교과 9 OpenCV 성능 개선 제안
- 제안 1: HSV 기반 병변 후보 마스크 추출 후 면적비 계산
- 제안 2: 불확실 분류(top1 점수가 낮고 클래스 간 점수 차가 작은 경우)를 `확인 필요`로 분기. 실제 결과 중 `angular_leaf_spot` 샘플은 0.4712 대 0.4657로 점수 차가 작았다.
- 제안 3: CNN 점수 + OpenCV 특징으로 ML 보조 판정
- 구현 여부: 설계 제안만 제출 (미구현)
- 성능 개선 실측: 없음 (개선 수치를 주장하지 않음)

## 9. 최종 판정 및 한계
- 필수 기능: 동기·비동기 API, Redis 캐시, Celery 큐, PostgreSQL 작업 기록이 실제 환경에서 동작함을 확인했다.
- 모델 분류 품질: Validation Accuracy 0.7669(Head-only 기준선). 시연 샘플 3장 중 `bean_rust` 1장이 오분류되었다. 이 3장은 정확도를 의미하지 않는다.
- 한계: Test 정량평가 미수행, 단일 Validation 133장·3 epoch 실험, 성능 측정은 이미지 1장·조건별 5회, 데이터 출처·현장 조명 조건 미검증
- 추후 과제: 별도 Test 평가, Full Fine-tuning 비교, 규칙 기반 검증 실험
